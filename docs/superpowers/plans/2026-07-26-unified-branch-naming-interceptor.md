# Unified Branch-Naming Interceptor Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace three wildcard branch-rename interceptors with one table-driven branch-naming interceptor that extracts each tool command once.

**Architecture:** A single stateful `BranchNamingInterceptor` extracts a matching command during `onToolStart`, routes every matching `[regex, handler]` tuple, and stores the matched handlers by session and tool-use ID for completion. The existing manual-rename, pre-push, and pre-PR side effects move into that class while `AutoGeneratedBranchRenamer` remains the focused owner of automatic rename behavior.

**Tech Stack:** TypeScript, Vitest, Express backend interceptor infrastructure, Biome

## Global Constraints

- Export only `createBranchNamingInterceptor()` and `branchNamingInterceptor` from the new interceptor module.
- Remove all legacy branch-rename, pre-push-rename, and pre-pr-rename interceptor and factory exports.
- Register exactly one wildcard branch-naming interceptor.
- Call `extractMatchingCommand` once per normal tool-call lifecycle.
- Dispatch every matching route when one command contains multiple triggers.
- Preserve all current manual rename, push, PR cleanup, failure, retry, lifecycle, and bounded-state behavior.
- Key pending completion state by both `sessionId` and `toolUseId`.
- Keep `AutoGeneratedBranchRenamer` as a separate shared helper.
- Do not address the unrelated baseline `react-resizable-panels` type errors in `src/components/ui/resizable.tsx`.

Define the route model:

```ts
type PendingBranchNamingCall = {
  command: string;
  handlers: BranchNamingHandler[];
  remoteCleanupCandidate?: RemoteCleanupCandidate;
};

type BranchNamingHandler = {
  name: 'manual-rename' | 'push' | 'pr-create';
  onStart?: (
    event: ToolEvent,
    context: InterceptorContext,
    pending: PendingBranchNamingCall
  ) => Promise<void>;
  onComplete?: (
    event: ToolEvent,
    context: InterceptorContext,
    pending: PendingBranchNamingCall
  ) => Promise<void>;
};

type BranchNamingRoute = readonly [regex: RegExp, handler: BranchNamingHandler];
```

- [x] **Step 4: Implement one table-driven interceptor**

Implement a `BranchNamingInterceptor` with one
`AutoGeneratedBranchRenamer`, one bounded pending map, and this route order:
manual rename, push, PR create.

```ts
class BranchNamingInterceptor implements ToolInterceptor {
  readonly name = 'branch-naming';
  readonly tools = '*';

  private readonly renamer = new AutoGeneratedBranchRenamer();
  private readonly pendingCalls = new Map<string, PendingBranchNamingCall>();
  private readonly routes: readonly BranchNamingRoute[] = [
    [
      GIT_BRANCH_RENAME_TEXT_REGEX,
      { name: 'manual-rename', onComplete: this.completeManualRename },
    ],
    [
      GIT_PUSH_REGEX,
      { name: 'push', onStart: this.startPush, onComplete: this.completePush },
    ],
    [
      GH_PR_CREATE_REGEX,
      {
        name: 'pr-create',
        onStart: this.startPrCreate,
        onComplete: this.completePrCreate,
      },
    ],
  ];

  start(): void {
    this.renamer.reset();
    this.pendingCalls.clear();
  }

  stop(): void {
    this.renamer.reset();
    this.pendingCalls.clear();
  }
}
```

Implement handlers as arrow-function fields so table callbacks preserve the
class instance. Use `JSON.stringify([sessionId, toolUseId])` for the pending
key.

In `onToolStart`, do all routing and state insertion before the first await:

```ts
async onToolStart(event: ToolEvent, context: InterceptorContext): Promise<void> {
  const command = extractMatchingCommand(event, BRANCH_NAMING_TEXT_REGEX, logger);
  if (!command) {
    return;
  }

  const handlers = this.routes
    .filter(([regex]) => regex.test(command))
    .map(([, handler]) => handler);
  if (handlers.length === 0) {
    return;
  }

  const pending = { command, handlers };
  this.trackPendingCall(context.sessionId, event.toolUseId, pending);

  for (const handler of handlers) {
    await this.runHandler(
      handler,
      'start',
      () => handler.onStart?.(event, context, pending),
      event,
      context
    );
  }
}
```

In `onToolComplete`, delete the pending entry before invoking completion
handlers so duplicate completion events cannot repeat writes:

```ts
async onToolComplete(event: ToolEvent, context: InterceptorContext): Promise<void> {
  const key = pendingCallKey(context.sessionId, event.toolUseId);
  const pending = this.pendingCalls.get(key);
  if (!pending) {
    return;
  }
  this.pendingCalls.delete(key);

  for (const handler of pending.handlers) {
    await this.runHandler(
      handler,
      'complete',
      () => handler.onComplete?.(event, context, pending),
      event,
      context
    );
  }
}
```

`runHandler` must catch and log each route's exception separately, including
the handler name, phase, workspace, session, and tool-use ID. This preserves
the registry's current failure isolation when one command matches multiple
routes: one handler failure cannot prevent the remaining handlers from
running. Use this signature:

```ts
private async runHandler(
  handler: BranchNamingHandler,
  phase: 'start' | 'complete',
  run: () => Promise<void> | undefined,
  event: ToolEvent,
  context: InterceptorContext
): Promise<void>
```

Port the three behaviors exactly:

- `completeManualRename` first validates
  `containsGitBranchRenameCommand(pending.command)`, invalidates Git state even
  for a failed overall command, and only then applies the existing success,
  `rev-parse`, empty-name, and atomic persistence guards.
- `startPush` calls `renameIfAutoGenerated` with the existing push labels;
  `completePush` resets PR discovery only when `event.output?.isError` is
  false and logs reset failures.
- `startPrCreate` calls `renameIfAutoGenerated` with the existing PR labels and
  stores a cleanup candidate on `pending` when a rename returns an old branch;
  `completePrCreate` consumes that candidate only after successful PR creation
  and catches remote cleanup exceptions.

Bound `pendingCalls` with the same delete-oldest behavior used by the current
two pending maps. Export only:

```ts
export function createBranchNamingInterceptor(): ToolInterceptor {
  return new BranchNamingInterceptor();
}

export const branchNamingInterceptor = createBranchNamingInterceptor();
```
